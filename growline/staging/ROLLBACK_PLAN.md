# Integration rollback and operations plan

No staging/production action was executed. Use only an explicitly approved target and operator. Two apps/projects remain independent.

1. Before release record both Git SHAs, Functions versions, web artifacts, rules/index hashes, runtime configuration and secret version IDs (never values), backup references and operator. A first rollout with no earlier safe artifact has no automatic rollback target.
2. Disable INTEGRATION_HANDOFF_ENABLED and INTEGRATION_ACTIVITY_ENABLED on BOTH runtimes. Keep INTEGRATION_SSO_ENABLED and GROWLINE_JOBS_ENABLED false. Redeploy only approved affected target endpoints/server; pause code issuance. Confirm disabled mutation responses and no new cross-project writes. Already issued codes expire, but global disable also blocks redemption.
3. Retain successful canonical members, identity mappings, operations, consent and audit. Do not delete successes or reset idempotency keys to roll back UI/code. Quarantine pending/manual-review/conflicting work for inspection.
4. Club-side owner revocation is destination-authoritative. It does not silently mutate GrowLine's independent link record; the source may look stale until unlink/refresh. Historical successful handoffs remain reconcilable after relationship revocation.
5. Global disable prevents network reconciliation and source unlink mutations. Inspect authenticated status reads; recover under a controlled approved activation window using exact stored keys/requests. Respect the eight-attempt budget. Ambiguous matches require reviewed identity evidence, not guessed matches.
6. Restore known-safe web/Functions artifacts while keeping all relevant flags false. App Hosting rollback restores the selected artifact's environment as well as its code; do not restore an enabled artifact blindly. Never restore anonymous/PIN authorization rules. Preserve deployed indexes required by surviving reads.
7. Disable scheduled API/Functions job flags and schedules before restoration. Preserve checkpoints, audit and notification claims. Unknown notification delivery needs operator review before claim reset. A real retention purge cannot be reversed by fabricating deleted health data.
8. Future SSO rollback must advance durable pair/session epochs and revoke each app's own session, with failed peer revocation visibly pending. Never delete operational member records to revoke sign-on. SSO is implemented locally and remains disabled in hosted environments. Before rollback, deliver pending revocations while retaining peer origins and signing-key bindings; disable new exchanges on both servers, preserve pair/session epochs, durable outbox and audit history, then disable browser entry.
9. Re-run station operations, workspace isolation, owner privacy, PIN/financial/Storage denials and no-automatic-finance checks. Reconcile accepted operations once during controlled recovery; record sanitized evidence. Remove only approved synthetic staging fixtures under a reviewed retention policy, never customer records/history needed for diagnosis.

## Monitoring required before production

Assign a monitoring owner, rollback owner, incident channel and reviewed thresholds for invalid server assertions, payload conflicts, pending-operation age/attempt exhaustion, manual-review backlog, duplicates, unavailable owner aggregates, revoked/stale relationships, job failures, retention checkpoint backlog/skip counts, scan budgets and unknown provider delivery. Log operation identifiers and safe error categories, not tokens, signing keys, phone numbers, notes or health data. Confirm backup restore procedures and retention/audit policy before production activation.
